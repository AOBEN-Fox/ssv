# T2 BoT-SORT 迁移说明

## 背景

本说明记录 `gst/ssv-track` 从原有 IoU 跟踪替换为 BoT-SORT Lite 的落地结果。迁移目标是把跟踪能力收敛到仓内原生插件实现，同时保留现有检测元数据契约、插件边界和 `mock-track` 旁路能力。

本次迁移属于 `T2` 感知算法与元数据主线，重点影响 `gst/ssv-track`、`gst/ssv-pub`、`gst/ssv-overlay`、`gst/tests` 和 `scripts/test.sh`。

## 迁移内容

### 代码结构

- 将跟踪实现拆分到 `gst/ssv-track/botsort/`。
- 保留 `gst/ssv-track/gstssvtrack.cpp` 作为 GStreamer 胶水层。
- 保留 `mock-track` 作为显式旁路模式，用于联调和无状态 smoke。

### 文件职责与协作关系

BoT-SORT 迁移后的代码按“插件边界、算法 DTO、基础算法、轨迹对象、主流程、测试”分层。头文件（`.hpp`）声明稳定的数据结构和接口，源文件（`.cpp`）实现对应算法；算法内核不依赖 GStreamer、Redis 或 `SsvDetectionStore`。

#### 插件边界文件

| 文件 | 详细职责 | 不负责的内容 |
| --- | --- | --- |
| `gst/ssv-track/gstssvtrack.hpp` | 声明 `ssvtrack` GStreamer 类型、插件对外可见的类型接口和注册所需声明。 | 不实现 BoT-SORT 匹配、Kalman 或轨迹生命周期。 |
| `gst/ssv-track/gstssvtrack.cpp` | GStreamer 胶水层。注册 `ssvtrack` 属性；在 `start()` 根据 GObject 属性生成 `TrackerConfig` 快照并创建 tracker；在 `stop()/finalize()` 释放 tracker；从 `SsvDetection` 读取检测；将归一化 bbox 转成像素坐标；映射 BGR `GstBuffer` 为 `FrameView` 供 GMC 使用；调用 `BoTSortTracker::update()`；将 `track_id`、`track_state`、`occluded` 写回 `SsvDetectionStore`。 | 不维护 IoU/Hungarian 细节，不直接操作轨迹池，不把 Redis 或下游事件逻辑放进 tracker。 |

插件层的配置来源是 GObject 属性。`start()` 时通过配置快照函数一次性转换为 `TrackerConfig`，避免 GObject 属性和算法配置长期保存两份可变状态。`mock-track=true` 时绕过真实 tracker，仅用于联调和 smoke。

#### 算法数据类型与坐标适配

| 文件 | 详细职责 | 关键内容 |
| --- | --- | --- |
| `gst/ssv-track/botsort/botsort_types.hpp` | 定义算法内核和插件之间传递的轻量 DTO、枚举和配置。 | `Detection` 保存 bbox、score、类别、输入索引及跟踪写回字段；`FrameView` 保存图像指针、宽高和 stride；`TrackState` 表示 NEW/MATCHED/LOST/REMOVED 等状态；`TrackerConfig` 保存阈值、buffer、帧率、GMC 和开关；`UpdateResult` 同时返回当前帧检测映射与 `DebugStats`。 |
| `gst/ssv-track/botsort/botsort_coordinates.hpp` | 提供插件坐标契约与算法坐标契约之间的无状态转换。 | `to_pixel_detection()` 将 `[0,1]` 归一化坐标乘以帧宽高；`to_normalized_detection()` 在写回前恢复归一化坐标；无效宽高时保持源值，避免除零。 |

坐标转换只发生在插件边界，算法内部始终使用像素坐标。这样 GMC 的仿射变换、IoU 计算和 Kalman 的中心点/宽高状态使用同一单位。

#### Kalman 运动模型

| 文件 | 详细职责 |
| --- | --- |
| `gst/ssv-track/botsort/botsort_kalman.hpp` | 声明 `KalmanState` 和 `BoTSortKalman` 接口。状态包含 8 维均值、协方差以及初始化标志；接口包括 `initiate()`、`predict()`、`update()` 和批量 `multi_predict()`。 |
| `gst/ssv-track/botsort/botsort_kalman.cpp` | 实现 8 维常速度模型、4 维观测投影、协方差传播和更新。内部提供固定尺寸矩阵乘法、转置、求逆、噪声标准差和状态转移矩阵等辅助函数。检测框先转换为中心点、中心点、宽高（`xywh`）观测，再用于 Kalman 更新。 |

Kalman 只负责运动状态估计，不负责轨迹 ID 分配、检测筛选或匹配阈值判断。

#### 匹配与代价计算

| 文件 | 详细职责 |
| --- | --- |
| `gst/ssv-track/botsort/botsort_matching.hpp` | 声明 `AssignmentResult` 以及 IoU cost、score fuse、类别兼容性、线性分配和输入顺序恢复接口。 |
| `gst/ssv-track/botsort/botsort_matching.cpp` | 实现 IoU 距离（`1-IoU`）、置信度融合代价（`1-(1-cost)×score`）、可选类别约束、Hungarian 最小代价分配、阈值过滤和按 `input_index` 恢复检测顺序。 |

该模块不决定当前使用第几阶段，也不创建轨迹；它只接收代价矩阵并返回匹配、未匹配行和未匹配列。阶段阈值由 `botsort_tracker.cpp` 按 BoT-SORT 主流程传入。

#### 单条轨迹对象

| 文件 | 详细职责 |
| --- | --- |
| `gst/ssv-track/botsort/botsort_track.hpp` | 声明 `BoTSortTrack`，封装单条轨迹的 ID、类别、状态、激活标志、bbox 和 Kalman 状态访问接口。 |
| `gst/ssv-track/botsort/botsort_track.cpp` | 实现单条轨迹的 `activate()`、`update()`、`re_activate()`、`mark_lost()`、`mark_removed()` 状态变化，以及检测框到 Kalman 测量值的转换。 |

`BoTSortTrack` 表示“一个目标”的状态，不持有整帧检测列表，也不执行 Hungarian 匹配。整帧轨迹池和 ID 递增由 `BoTSortTracker` 管理。

#### GMC 全局运动补偿

| 文件 | 详细职责 |
| --- | --- |
| `gst/ssv-track/botsort/botsort_gmc.hpp` | 声明 `GmcWarp` 仿射变换 DTO 和 `BoTSortGmc` 接口，包括 `estimate()`、`reset()`、失败回退状态查询以及 bbox 变换。 |
| `gst/ssv-track/botsort/botsort_gmc.cpp` | 实现 `none`/稀疏光流模式；对输入帧按 `gmc_downscale` 缩放，提取和跟踪特征点，估计仿射变换，并在失败、无帧或变换退化时返回 identity warp。 |

GMC 只修正相机或场景的整体运动，不替代目标级 Kalman 预测。`FrameView` 的内存由插件映射和解除映射，GMC 不拥有 `GstBuffer`。

#### BoT-SORT 主流程

| 文件 | 详细职责 |
| --- | --- |
| `gst/ssv-track/botsort/botsort_tracker.hpp` | 声明 `BoTSortTracker` 的两个 `update()` 重载（有帧和无帧），以及内部 `TrackRecord`、tracked/lost/unconfirmed/removed 轨迹池和辅助操作。 |
| `gst/ssv-track/botsort/botsort_tracker.cpp` | 编排完整每帧流程：过滤无效框；按 `track_low_thresh`、`track_high_thresh` 划分高低分检测；Kalman 预测；GMC warp；tracked+lost 与高分检测第一阶段关联；tracked 与低分检测第二阶段关联；unconfirmed 与剩余高分检测关联；处理 lost/removed TTL；按 `new_track_thresh` 创建新轨迹；去重并恢复输入检测顺序。 |

`BoTSortTracker` 是算法内核的唯一编排入口。它组合 `BoTSortKalman`、`BoTSortGmc`、matching 函数和轨迹池，但不依赖 GStreamer。`update()` 返回当前帧真正有跟踪结果的检测，插件再按 `input_index` 写回原始检测数组。

#### 每帧调用关系

```text
SsvDetectionStore
    │ 归一化检测 + SsvDetection::confidence
    ▼
gstssvtrack.cpp
    │ 属性快照、坐标转像素、可选 GstVideoFrame 映射
    ▼
BoTSortTracker::update()
    │
    ├─ 1. botsort_gmc：从当前帧估计 k-1 → k 的 warp matrix
    │
    ├─ 2. botsort_kalman：预测 tracked/lost 轨迹到当前帧 k
    │
    ├─ 3. botsort_gmc：将已求得的 warp 应用到预测轨迹
    │
    ├─ 4. botsort_matching：高分、低分和 unconfirmed 三阶段关联
    │
    ├─ 5. botsort_track：更新单条轨迹状态，处理 lost/removed/new
    │
    └─ 6. botsort_types：承载检测、帧、配置和结果 DTO
    ▼
gstssvtrack.cpp
    │ 恢复输入顺序、坐标转归一化、写回三项跟踪字段
    ▼
SsvDetectionStore → ssv-overlay / ssvpub
```

当前实现先估计 warp，再进行 Kalman 预测，最后将 warp 应用于预测轨迹；估计矩阵与 Kalman 预测相互独立，因此这两个步骤可交换。原始 Python 的语句顺序是 `multi_predict()`、`gmc.apply()`、`multi_gmc()`，即先预测、再估计并应用 warp；两者共同的算法约束是：关联前必须把 warp 应用于已预测的轨迹位置。上图描述的是本仓实际时序，不再将模块依赖误画为并列调用关系。

与原始 Python `bot_sort.py` 的对应关系是：`botsort_tracker.cpp` 对应 `update()` 主流程，`botsort_kalman.cpp` 对应 Kalman 预测/更新，`botsort_matching.cpp` 对应 IoU/score fuse/Hungarian 关联，`botsort_gmc.cpp` 对应 GMC，`botsort_track.cpp` 承担 `STrack` 的单轨迹状态。ReID/embedding 路径不在本次迁移范围。

### BoT-SORT 参数说明

当前默认值如下：

| 参数 | 默认值 | 含义 |
| --- | ---: | --- |
| `track-thresh` | `0.5` | 轨迹置信度参考线；当前主要用于将匹配结果标记为 `occluded`，不负责过滤检测。 |
| `track-low-thresh` | `0.1` | 检测最低保留分数，低于该值的检测直接丢弃。 |
| `track-high-thresh` | `0.6` | 高低分检测分界线；高于或等于该值进入第一阶段关联，否则进入低分第二阶段关联。 |
| `new-track-thresh` | `0.7` | 创建新轨迹的最低分数；未匹配检测低于该值时不会创建新的 `track_id`。 |
| `match-thresh` | `0.8` | 第一阶段轨迹-检测关联的代价阈值；代价超过该值时匹配被拒绝。 |
| `track-buffer` | `30` | 轨迹丢失后保留的帧数，超时后转为 removed。 |
| `frame-rate` | `30` | 用于按帧率缩放 `track-buffer` 的生命周期。 |
| `gmc-method` | `sparse-opt-flow` | 全局运动补偿方法；当前支持稀疏光流和 `none`。 |
| `gmc-downscale` | `2` | GMC 估计前的图像缩放倍数，数值越大通常越快但精度可能下降。 |
| `enable-score-fuse` | `true` | 是否将检测置信度融合到关联代价中。 |
| `enable-class-constraint` | `false` | 是否要求轨迹类别与检测类别一致；按原始 Python BoT-SORT 流程关闭。 |
| `mock-track` | `false` | 测试旁路，开启后不运行真实 BoT-SORT，只分配顺序 ID。 |

阈值之间的处理关系为：

```text
score < track-low-thresh
    → 丢弃

track-low-thresh ≤ score < track-high-thresh
    → 低分检测，进入第二阶段关联

score ≥ track-high-thresh
    → 高分检测，进入第一阶段关联

未匹配高分检测且 score ≥ new-track-thresh
    → 创建新轨迹
```

例如默认配置下，分数为 `0.55` 的检测属于低分检测，只能参与第二阶段补关联；分数为 `0.7` 的检测进入第一阶段，但只有在匹配代价不超过 `match-thresh=0.8` 时才能续接已有轨迹；如果未匹配且分数达到 `new-track-thresh=0.7`，才会创建新轨迹。

`track-high-thresh` 和 `match-thresh` 的职责不同：前者只决定检测进入哪一阶段，后者决定轨迹与检测的空间/置信度匹配是否被接受。以 score fuse 为例，若 IoU 为 `0.4`、检测分数为 `0.8`，关联代价为 `1 - 0.4 × 0.8 = 0.68`，在 `match-thresh=0.8` 下可以匹配；若将 `match-thresh` 降为 `0.5`，同一匹配会被拒绝。低分第二阶段和未确认轨迹阶段使用各自固定的关联阈值，不直接复用插件的 `match-thresh`。

## 结果

### 静态验证

- `./ssv build` 通过。
- `meson test -C build --print-errorlogs` 通过。
- `agent` 单测通过，结果为 `7 passed`。

### 运行时验证

- 真实链路 `./ssv test` 已通过到链路冒烟阶段。
- 使用 `rtsp://localhost:8554/stream` 的 live pipeline smoke 通过。
- 额外执行了 20 秒有界运行验证：`./ssv agent` + `timeout 20s ./ssv run --skip-build`。
- 该窗口内从 Redis 流 `ssv:events` 抽样统计到 183 个 detection，其中 170 个已写回 `track_id >= 1`，13 个仍为 `track_id = -1`。
- 该窗口内未观察到 `occluded=true`，说明当前流和阈值组合下遮挡分支未被明显触发。
- 抽样轨迹 ID 在窗口后段稳定收敛到少数主目标，主轨迹连续性可接受，新增目标会分配新的正整数 ID。
- `mock-track=true` 路径可正常输出顺序递增 ID，适合作为联调旁路。
- 默认 BoT-SORT 路径在当前流上可以工作。
- 在当前流和模型组合下，`gmc-method=none` 比默认 `sparse-opt-flow` 更稳定。

## 影响

### 对上游调用方的影响

- 现有 `ssv_meta` 字段保持稳定，消费方不需要因为这次迁移修改解析逻辑。
- Redis 事件仍然是 detection 级别消息，Agent 消费链路不需要改 schema。
- 只要调用方依赖 `track_id`、`track_state`、`occluded`，现有逻辑可以继续工作。

### 对运行参数的影响

- 默认跟踪器已经从 IoU 切换为 BoT-SORT。
- 当前流下建议优先使用 `gmc-method=none` 作为生产默认或首选调参起点。
- `mock-track` 不应被当作真实跟踪模式使用，只保留为旁路验证和 smoke。

### 对测试的影响

- `agent` 测试依赖 `uv` 管理的虚拟环境，不再假定系统存在独立 `pytest` 命令。
- `./ssv test` 现在同时覆盖 C++、Python Agent 和链路冒烟三段验证。

## 边界

### 已明确不做

- 不新增轨迹级 Redis schema。
- 不引入 ReID、embedding、跨摄像头跟踪或 Python 运行时依赖。
- 不修改 `SsvDetectionStore` 的状态机语义。
- 不改变 bbox 归一化坐标格式。
- 不把 `mock-track` 改造成默认或隐藏模式。

### 需要后续单独处理的问题

- `gmc-method` 的最佳默认值需要结合更多流和模型做回归，不建议只凭单条流经验一锤定音。
- 如果未来要输出轨迹级对象，需要单独设计事件 schema 和消费端兼容策略，不能在当前 detection 级契约上直接叠加。

## 结论

这次迁移已经完成从 IoU 到 BoT-SORT Lite 的内核替换，且真实 RTSP 链路、插件测试、Agent 测试均已验证通过。额外的 20 秒实测表明，BoT-SORT 在当前流上能够持续写回稳定 track ID，主目标续接正常，仍有少量低分检测保持 `track_id = -1`，属于当前阈值与场景下的可接受现象。当前仓内的对外契约保持稳定，`mock-track` 旁路仍可用于联调和 smoke；在当前环境下，`gmc-method=none` 是更稳的运行起点。

## 推荐运行参数

- 生产或准生产验证优先使用默认 BoT-SORT 路径，并显式设置 `gmc-method=none`。
- 需要联调时可以打开 `mock-track=true`，但不要把它作为真实跟踪结果对外解释。
- 如果要观察检测框叠加效果，可以在 `./ssv run --display` 下额外打开可视化分支。
- 如果要排查跟踪稳定性，先固定流、模型和阈值，再比较 `gmc-method=none` 与默认 `sparse-opt-flow` 的输出差异。

## 排障顺序

1. 先确认 `ssvtrack` 插件能被 `gst-inspect-1.0` 识别。
2. 再确认 `ssvpub` 对应的 Redis 容器在线。
3. 然后用 `./ssv test` 验证 C++、Agent 和基础链路。
4. 接着在真实 RTSP 流上跑 `scripts/pipeline.sh --smoke --skip-build`。
5. 如果 `track_id` 仍然大量为 `-1`，先尝试 `gmc-method=none`，再看模型输出和阈值设置。
6. 若 `mock-track=true` 能正常出 ID 而 BoT-SORT 不稳定，优先检查检测质量、阈值和输入流抖动，而不是先怀疑发布链路。
